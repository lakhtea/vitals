# 13 - Agent connection

> Milestone 13 built the boundary the triage agents cross: an MCP server whose tools are thin wrappers over the GraphQL schema, a service token for the two mutations only agents call, a health probe that watches applications which push nothing, and the per-device and per-connection breakdown an agent needs to reason about a regression.
> Nothing in this milestone calls a model.
> This chapter explains what MCP is from first principles, why the tools are thin, how service authentication differs from user authentication, and why the dashboard still never talks to an LLM.

## What was built

- `services/vitals-mcp`: an MCP server over stdio with four tools: `list_open_incidents`, `get_incident_context`, `record_step`, `request_human_review`.
  It calls `/api/graphql` over HTTP with a service token; `.mcp.json` registers it so Claude Code in this repo can use the tools.
- Service authentication: `VITALS_SERVICE_TOKEN`.
  Two new mutations require it: `recordStep` (an agent writes a timeline entry) and `transitionIncident` (an agent moves an incident along its own path, and only that path).
- `Incident.breakdown`: p75 and sample counts per device class and per connection type, over exactly the two windows frozen in the incident's evidence.
- `npm run checks:probe`: fetches any HTTP health endpoint once, classifies it as ok, degraded, or failing, and pushes the verdict to `/api/checks`.
- The incident page says when the agents have stopped at the human gate.

## What MCP is

### The problem it solves

A model can only act on the world through tools its host gives it.
Before MCP, every host (an IDE, a chat app, an agent framework) defined tools its own way, so a tool written for one host had to be rewritten for the next.
The Model Context Protocol, published by Anthropic in late 2024 and now implemented by many hosts, standardises that seam: a server describes its tools once, and any MCP host can list them, show their descriptions to its model, and call them.

### The pieces

- **Host and client.** The host is the application the model runs in (Claude Code, a desktop app, the M15 worker). It creates one MCP client per server it connects to.
- **Server.** A process that offers capabilities. Ours is `services/vitals-mcp`.
- **Messages.** JSON-RPC 2.0: every request has an id, a method, and params; every response carries the same id with a result or an error.
- **Lifecycle.** The client sends `initialize` with its protocol version and capabilities, the server answers with its own, and only then do ordinary requests flow.
  `tools/list` returns each tool's name, description, and JSON Schema for its input; `tools/call` runs one.

### Three kinds of capability

- **Tools** are functions the model decides to call, with typed inputs. All four of ours are tools.
- **Resources** are data the host can read by URI and put in front of the model, chosen by the application rather than the model.
- **Prompts** are templates a person picks, like slash commands.

Incidents could have been resources, but the agents need to choose which incident to read and then act on it, so tools are the honest fit.

### Transports

- **stdio.** The host starts the server as a child process and the two exchange newline-delimited JSON over its stdin and stdout.
  This is what `.mcp.json` sets up, and why the server never prints to stdout: one stray `console.log` is a corrupt protocol message.
  Diagnostics go to stderr.
- **Streamable HTTP.** The server listens on a URL and clients connect over HTTP, which suits a server shared by many hosts.
  M15's worker can move to it if the MCP server becomes its own deployable.

### Two kinds of failure

A JSON-RPC error means the protocol itself failed: an unknown method, malformed params.
A tool that ran and failed is different: it returns a normal result with `isError: true` and a text explanation.
The distinction matters because the model sees tool errors and can recover from them ("cannot move from open to awaiting human" tells it to walk the path first), while protocol errors are for the host.
Every tool here turns a GraphQL error into a tool error rather than throwing.

## Why the tools are thin wrappers over GraphQL

Each tool runs one or two typed GraphQL documents generated by the same codegen as the dashboard, so the agents and the people read the same data through the same resolvers and the same tests.
A tool list is also a security boundary.
The schema has `approveIncident` and `dismissIncident`; no tool calls them, so no agent can take the human's decision, however it is prompted.
And `transitionIncident` itself refuses any target outside the agent path, so even a client that bypassed the MCP server and held the token could not approve anything.
That is defence in depth: the tool list keeps honest agents on the path, the resolver keeps everything else off it.

The descriptions are written for the reader that matters: a model deciding which tool to call.
Each says what the tool does, when to use it, and what comes back, in the vocabulary the model will see in the data.

## Service tokens versus user authentication

User authentication answers "which person is this", usually with a session and a login.
Service authentication answers "is this one of our own programs", with a shared secret the program presents on every request.
Vitals is single-tenant and self-hosted, so v1 authenticates no people: anyone who can reach the dashboard can approve or dismiss.
Agents are different on two counts: they run unattended, and they spend money.
So the two mutations only agents call require `Authorization: Bearer <VITALS_SERVICE_TOKEN>`, compared in constant time, refused with an `UNAUTHENTICATED` error before anything is read.
The server-rendered pages build their GraphQL context without a request, so they are never mistaken for an agent.
The bearer parsing and the constant-time comparison are shared with `/api/checks` in `src/auth/bearer.ts`, so there is one implementation of "present a secret" in the codebase.

## Why the app still never calls a model

The plan's guardrail is that the Next.js app never calls a model, and M13 keeps it: the MCP server is a translator between a protocol and an API, with no model behind it.
The models live in whatever host connects: Claude Code today, the M15 worker later.
That keeps the dashboard cheap to run, free of API keys, and deterministic to test; every behaviour in this milestone has a test that runs without a network or a key.

## The health probe

`/api/checks` assumes an application that reports on itself.
Many do not, but nearly all expose a `/healthz`-style URL.
`npm run checks:probe -- --site demo --url <url>` fetches it once with a timeout, times the round trip, and classifies the answer: a 2xx inside the latency budget is ok, a slow 2xx is degraded (the detail says by how much), any other status or no answer is failing.
It then pushes that verdict with the site's write key, exactly as an application would, so everything downstream (the health panel, the detector, the incidents) works unchanged.
Run it from cron or a CI schedule; the detector's degraded streak of three means a single slow probe never opens an incident.

## The breakdown

An agent asked "why did LCP on /pricing regress" needs to know whether it regressed for everyone or for one kind of visitor.
`Incident.breakdown` answers with p75 and sample counts per device class and per connection type, over exactly the baseline and current windows the detector compared, read from the evidence rather than from the clock, so the numbers never drift from what opened the incident.
It is computed when asked, two statements (one per dimension), and is null for health-check incidents.

## Why every new file exists

The MCP server, in `services/vitals-mcp/`, inside the root toolchain (one package.json, one lint, one Vitest run):

- `client.ts`: a small GraphQL-over-HTTP client that sends typed documents with the service token and turns GraphQL errors into one error carrying their messages.
  Its `fetch` is injectable, which is how the tests point it at an in-process Yoga.
- `documents.ts`: the five operations the tools run, typed by codegen from the same schema as the dashboard's queries, so a schema change breaks the tools at compile time.
- `generated/`: codegen's output for those five documents only.
  The first version shared the dashboard's generated module, and the client preset puts every document it is given into one map that whoever imports `graphql()` bundles: the browser was downloading the agents' operations.
  The bundle check caught it (the overview route grew 14,849 bytes in a milestone that did not touch the overview); `codegen.ts` now has one output per consumer, and the route is back to its M12 size.
- `tools.ts`: each tool's name, description for the model, zod input schema, and handler; `runTool` turns any failure into a tool result with `isError: true`.
- `server.ts`: registers the four tools on an `McpServer` named `vitals`.
- `main.ts`: the stdio entry; reads `VITALS_URL` and `VITALS_SERVICE_TOKEN`, refuses to start without the token, writes diagnostics to stderr only.
- `README.md`: the tools and how to run them, for someone who lands in the folder.
- `tools.test.ts`: a real MCP client talks to the server over the SDK's in-memory transport; the server's GraphQL client calls a real Yoga on a seeded in-memory database.
  Every tool is exercised through the protocol, including the error paths.
- `.mcp.json` at the repo root: registers the server with Claude Code; the token comes from your environment, never from the file.

The app side:

- `src/auth/bearer.ts`: bearer parsing and constant-time comparison, extracted from the checks handler so the write key and the service token share one implementation.
- `src/graphql/context.ts`: `isService` and `requireService`; the Yoga route now hands the request to `createContext`.
- `src/db/queries/steps.ts`: `recordStep`, one transaction that validates, inserts the step, and bumps the incident's `updated_at`.
- `src/db/queries/incidents.ts` gained `transitionIncident`, which checks the agent path and the transition table before writing.
- `src/db/queries/breakdown.ts`: two statements, one per dimension, each ranking both windows at once with the same nearest-rank percentile as the dashboard.
- `src/incidents/vocabulary.ts` gained `AGENT_TRANSITION_TARGETS`, the agent path written down once.
- `src/graphql/inputs.ts`, `types/incidents.ts`, `schema.ts`: `StepUsageInput`, `BreakdownRow`, `IncidentBreakdown`, `Incident.breakdown`, and the two mutations.
- `src/checks/probe.ts` and `scripts/check-probe.ts`: the probe's classification (pure, tested against a real local HTTP server) and its CLI.
  The CLI wraps its work in an async `main`, because this package is CommonJS and has no top-level `await`; running it caught that, the type checker did not.
- `src/app/incidents/[id]/page.tsx`: the "nothing leaves the repository until you approve" notice when an incident is awaiting a person.
- Tests: `src/graphql/agent-mutations.test.ts` (token, agent path, steps, breakdown), `src/checks/probe.test.ts`, `services/vitals-mcp/tools.test.ts`, and `e2e/agent-steps.spec.ts`, where a scripted agent with the token walks an incident to the gate and the page shows its step.

Not done here, on purpose: `get_incident_context` does not include a sample of recent sessions on the regressed path, because the schema has no path filter on sessions yet and the summarize agent in M15 will show whether it is needed.

## How to see it working

```bash
npm run db:seed && npm run incidents:detect
export VITALS_SERVICE_TOKEN=local-dev-token
npm run dev            # in another terminal, with the same VITALS_SERVICE_TOKEN exported
```

Open this repo in Claude Code; `.mcp.json` registers the `vitals` server and it starts with the token from your environment.
Ask it to list open incidents, then to read the context of the `/pricing` one.
Ask it to record a summarize step on that incident; reload `/incidents/<id>` and the step is in the timeline with whatever model and token counts it reported.

Probe something:

```bash
VITALS_WRITE_KEY=demo-write-key npm run checks:probe -- --site demo --url https://example.com/
```

Try the gate: ask the agent to approve the incident.
It has no tool for that, and if you send `transitionIncident(to: APPROVED)` by hand in GraphiQL with the token, the resolver refuses it.

## Self-check

1. What is the difference between an MCP tool and an MCP resource, and why are incidents exposed as tools?
2. Why must a stdio MCP server never write to stdout?
3. A tool call fails because the incident is in the wrong state. Should the server return a JSON-RPC error or a tool result with `isError: true`, and why?
4. Name the two independent things that stop an agent from approving an incident.
5. Why does the server-rendered incident page never count as an agent, even on the same machine that holds the token?
6. Why does the breakdown read its windows from the incident's evidence instead of from "the last 24 hours"?

<details>
<summary>Answers</summary>

1. A tool is a function the model chooses to call with typed inputs; a resource is data the host application chooses to read by URI. The agents must pick which incident to look at and then act on it, which is model-driven, so tools fit.
2. On stdio, stdout is the protocol channel: the host parses every line as a JSON-RPC message, so any other output corrupts the stream. Diagnostics go to stderr.
3. A tool result with `isError: true`. The protocol worked; the operation failed for a reason the model can act on, so the model must see it. JSON-RPC errors are for protocol failures the host handles.
4. No MCP tool calls `approveIncident` or `dismissIncident`, and `transitionIncident` refuses any target outside the agent path, so even a direct GraphQL call with the token cannot approve.
5. The RSC client builds its GraphQL context without a request, so there is no `Authorization` header to check and `isService` is false; only HTTP requests carrying the token are agents.
6. The incident is a claim about two specific windows. Reading "the last 24 hours" would describe a different period every time it is asked, so the breakdown could disagree with the evidence that opened the incident.

</details>
